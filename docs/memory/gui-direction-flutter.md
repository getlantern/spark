Spark needs a product GUI (no real one exists yet — only the macOS NE harness `platforms/apple/Sources/SparkApp` and the Android M9 demo `platforms/android/demo`). Direction as of 2026-06-18:

- **Mobile support is a firm requirement** — this is the deciding constraint. It rules out Dioxus (mobile is experimental/not production-grade) and favors Flutter (mature desktop + iOS/Android, one codebase).
- **Leaning Flutter, reusing a pared-down version of `getlantern/lantern`'s v9 Flutter UI** (org continuity; v9 is Flutter). Tauri 2 has mobile but is younger; the backend is UI-agnostic so a Tauri experiment later is cheap.
- **Open to experimenting with multiple UIs** — the [[m11-transport-candidates-anytls-samizdat]]-era backend contract (ADR 0004) is a clean UI-agnostic surface, so each UI is a thin frontend.

**Why:** the user wants mobile + desktop from one effort and to leverage the existing Lantern v9 UI/team familiarity.

**Agnostic core LANDED 2026-06-18 (commit `347fc7e`):** the UI-agnostic surface is now a real crate, **`spark-backend/`** — a typed async `Backend` over `spark_ipc::Client` (connect/disconnect/status/capabilities/details/metrics, profile CRUD, reconnecting `run_subscription`) that returns plain `spark-ipc` types, has **no binding annotations**, and owns **no runtime** (it's `Clone`, just the endpoint path). Every frontend is a thin layer whose dependency arrow points *into* it: `spark-ffi` is now just a UniFFI binding over `spark-backend` (mirror types + owned tokio runtime + `clone`+`spawn` delegation); the planned `flutter_rust_bridge` desktop bridge, Tauri, Dioxus, and the CLI all wrap the same crate. Don't put control logic in a binding — it goes in `spark-backend`.

**How to apply / integration shape (the load-bearing detail):** spark's core is **Rust** (not v9's Go core), so reusing the lantern Flutter UI means swapping the backend binding:
- **Mobile**: Flutter → platform channel → native VpnService/NE (Kotlin/Swift) which runs the tunnel via the `platforms/{android,apple}` shims (`run_fd`/`spawn_tunnel`) and can use the **UniFFI Kotlin/Swift bindings** from `spark-ffi` (→ `spark-backend`).
- **Desktop**: DONE 2026-06-18 (commits `d84d52b` crate+bindings, `df46099` native build+default, `404d6ca` runtime test). **`spark-bridge/`** = a thin **`flutter_rust_bridge`** crate over `spark-backend` (opaque `SparkBridge` owning a tokio runtime, `block_on`s the delegated calls, same owned-runtime model as `spark-ffi`). Dart: `gui/lib/frb_backend.dart` = `FrbBackend implements SparkBackend`, now the **desktop default** in `main.dart` (graceful fallback to `CliBackend` if `RustLib` can't init). frb toolchain pinned at **2.12.0** across codegen CLI + `flutter_rust_bridge` crate + Dart package (all three must match); config `flutter_rust_bridge.yaml`, generated Dart+Rust checked in (regen: `flutter_rust_bridge_codegen generate`). **Native build** via the `gui/rust_builder/` cargokit plugin — `flutter build` compiles+force-loads `spark-bridge` into `spark_bridge.framework`. **GOTCHA:** the cargo package had to be renamed `spark-bridge`→`spark_bridge` (underscore) because cargokit builds `lib<package>.a` verbatim but cargo normalizes `-`→`_` (dir stays `spark-bridge/`). **Runtime-verified** end-to-end via `gui/integration_test/frb_bridge_test.dart` (`flutter test integration_test -d macos`): bridge loads + FFI round-trips a typed error. **REMAINING:** successful-connect live gate (needs a running `spark-service` + sandbox disabled / socket entitlement for `/var/run/spark.sock`); richer screens off the ADR-0004 contract (would expand the `spark-bridge`+`SparkBackend` surface beyond connect/disconnect/status).
- **Mobile control gap**: the rich ADR-0004 contract (profiles/metrics/logs) lives in `spark-service` (desktop). Mobile has no daemon, so the **first mobile cut = connect/disconnect/status via the shim**; full mobile profile mgmt is a later in-app control path.

Desktop vs mobile are **separate apps** (different tunnel-ownership: desktop = unprivileged GUI ↔ privileged `spark-service` over IPC; mobile = app IS the privileged VpnService/NE, in-process) but share the `spark-ffi`/`spark-ipc` contract.
